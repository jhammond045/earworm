# M1: engine core

M1 builds the engine from the [TDD](TDD.md) build order: voices, the drum model, space, the sequencer and transport, the rings and the offline host. Its gate is **8 layers with no dropouts**, and it has to measure two numbers the TDD only estimated: the partial budget and the offline render speed on the reference laptop (2020 M1 MacBook Air, Chrome).

This page says how to run it, how to judge the gate (including the steps to run on the reference laptop), what is built and what was measured on the build machine.

## Run it

```sh
pnpm install
pnpm dev
```

Open the URL Vite prints. The index page lists the M0 pages and two new ones:

- **`m1.html`, the player.** Press Start, then Play. The 8-layer demo song plays in the AudioWorklet. Each layer has a mute, a level slider, a peak meter and a voice count; the engine stats show CPU load, the partial budget, active partials and voices, steals and overloads. Export WAV renders the song in a worker, faster than real time, and downloads it.
- **`bench.html`, the benchmark.** See "Judge the gate" below.

The built `klont.wasm` is committed in `web/public/wasm`, so no Rust toolchain is needed to run the pages. With `cargo` on the PATH, `pnpm dev` rebuilds all wasm modules first.

Tests: `pnpm test` runs Vitest and then `cargo test --workspace`. Other commands:

| Command | What it does |
| --- | --- |
| `cargo run --release -p klont --bin bench` | Native benchmark: worst case per budget, then the demo song (`--seconds N`, `--json`) |
| `pnpm gen:params` | Regenerates the parameter table files from `crates/params/params.toml` |
| `pnpm gen:demo` | Rewrites the demo song blobs in `web/public/m1/demo` (the native benchmark reads them) |
| `pnpm build:wasm` | Rebuilds engine, analysis and klont wasm |

## Judge the gate

The gate is the TDD performance row "8 layers playing: no dropouts, under 50% of one core", measured as offline render speed above 4x real time on the reference laptop. Only someone with the laptop can run it.

**On the 2020 M1 MacBook Air:**

1. Plug in the charger, quit other apps, and close other Chrome tabs.
2. In the repo, run `pnpm install` once, then `pnpm dev`, and open `http://localhost:5173/bench.html` in Chrome. The page should say `crossOriginIsolated: true`.
3. Press the four buttons in order and wait for each to finish:
   1. **Offline: worst case** (about a minute). 8 layers x 8 held voices with all 64 partials audible, vibrato on every voice, delay and reverb on every layer, rendered for 10 s at each budget from 4096 down to 512 partials. Each row gives the real-time factor and the share of one core.
   2. **Offline: demo song** (a few seconds). 60 s of the demo song.
   3. **Block timing** (a few seconds). The worst case in 128-frame blocks, the size the worklet uses: p50, p99 and the slowest block, against the 2.67 ms quantum.
   4. **Live: 8 layers** (60 s). Plays the demo song through the worklet with the automatic budget and logs load, budget, overloads and steals once a second. Listen through it for clicks or gaps.
4. Read the Result section. It gives the recommended partial budget (the highest budget whose worst case runs above 4x real time) and a PASS or FAIL line for the offline gate.
5. Press Download JSON and keep the file, or send it on, so the numbers can go into this page.

**Pass:** the Result line says PASS, test 3 shows 0 blocks over the quantum, and test 4 plays the full minute with no audible clicks or gaps.

Optionally, for comparison, run `cargo run --release -p klont --bin bench` in a terminal on the same laptop (needs Rust from rustup.rs).

If the worst case falls under 4x at budget 4096, the page recommends a lower budget. The engine then needs that budget as its ceiling (`BUDGET_MAX` in `crates/klont/src/protocol.rs`), or the fixed per-layer cost needs to come down (see "Known limits").

## What was measured on the build machine

Build machine: Apple M4 MacBook Air, 10 cores, Chrome 154 (headless for the browser runs), 48 kHz.

**Worst case**, 10 s per budget:

| Budget | Active partials | Native: x real time | Native: core | Chrome wasm: x real time | Chrome wasm: core |
| --- | --- | --- | --- | --- | --- |
| 4096 | 4096 | 10.1 | 10.0% | 7.9 | 12.6% |
| 3072 | 3008 | 11.2 | 8.9% | 8.9 | 11.3% |
| 2048 | 1984 | 13.6 | 7.4% | 8.8 | 11.4% |
| 1536 | 1472 | 14.7 | 6.8% | 8.6 | 11.6% |
| 1024 | 960 | 16.7 | 6.0% | 10.0 | 10.0% |
| 768 | 704 | 17.7 | 5.7% | 11.1 | 9.0% |
| 512 | 448 | 18.9 | 5.3% | 11.6 | 8.7% |

| Measurement | Result |
| --- | --- |
| Demo song, offline | Native 18.3x real time; Chrome wasm 11.7x (60 s, budget 4096, peak 0.74, about 1300 partials) |
| Block timing, Chrome wasm, worst case at 4096 | Mean 0.34 ms, p99 0.37 ms, max 0.92 ms; 0 of 7500 blocks over 2.67 ms |
| Live, demo song in the worklet for 60 s | Budget stayed at 4096; 0 overloads; 0 steals; reported load 9 to 42% (see "CPU load in the worklet") |
| Export WAV | 71 s of audio in 9.2x real time |
| Partial cost, Chrome wasm | About 0.6 ns per partial per sample at full load |
| `klont.wasm` | 185 KB, no imports |

So on the M4 every budget clears 4x with room to spare, and the partial budget is not what limits the engine: at 4096 partials it costs 12.6% of a core in Chrome, against 8.7% at 512.

**What to expect on the reference laptop.** An M1 core is slower than an M4 core. If it is about 1.7 times slower, the Chrome worst case at 4096 comes out near 4.5x real time: a pass, with a thin margin. That is why the laptop run decides it. Dropouts in the live test could not be judged on the build machine: no one listened, and Chrome 154 does not expose `AudioContext.playoutStats`.

### What came from M0

- **Reused and extended:** the DSP crate (filters, bands, noise, frames, tuning, the live tier), with a delay line and the new effect modules added. Also the ring and meter-block helpers (`web/src/host/rings.ts`, where the meter block now takes its length) and the WAV writer (now stereo).
- **Replaced:** the one-layer synth and its ABI. The M1 engine is a new crate, `crates/klont`, built to the TDD ABI (`ew_init(sample_rate, max_block)`, `ew_buffers`, `ew_process`, `ew_render`, `ew_load`, `ew_seek`, plus `ew_free`). Its partial bank started from M0's: same rotator oscillators and ratio tables, but grouped four at a time with fast polynomial math. M0 also applied the drum ring rate twice, and that is fixed.
- **Kept as is:** the M0 engine (`crates/engine`, `engine.wasm`) and every M0 page still run unchanged. M2 moves the live tier into the new engine, and the M0 engine can be deleted then.

### How the engine works

- **Time.** Every call renders in spans that never cross a 32-sample control tick, counted from engine start. Each span is split again at every sequencer event, live trigger and note off, so each lands on its sample. Output is bit-identical however the host slices the calls (tested with 1, 7, 128, 1000 and 4096 samples).
- **Resolution, as built.**
  - **Step 1, morph:** not built. States and the morph lane arrive in M4.
  - **Steps 2 and 3, Influence and macros:** run when a stored value changes. The result is smoothed per tick with each parameter's `smooth_ms` and mapped to real units.
  - **Step 4, voice start:** a voice reads its layer's set, or for a beat layer its kit slot's set.
  - **Step 5, gesture:** for a voice playing a clip with a curve, the take's frame is read each tick and offsets a few parameters through fixed linear maps (`gesture_offsets` in `layer.rs`).
  - **Step 6, hit shape:** a beat voice offsets its slot's values by the hit's shape, scaled by Follow.
  - **Step 7, modulators:** run inside the voice.
  - **Smoothing:** happens on the layer sets, not per voice.
  - **The maps are provisional.** The gesture maps, the hit-shape maps and the macro weights are first guesses; M2 tunes them by ear.
- **Layer effects.** Space, crush and tape are per layer and always read the layer's own set, also on beat layers.
- **Partial budget.** One budget is shared by all voices. Each tick, voices that want more partials than the budget allows get a share in proportion to their loudness, and a cut removes the highest partials first without making the rest louder.
  - **Live:** the budget starts at 4096. When the host reports load above 0.8 it drops by 15% a block, down to 256. If it is at that floor and load passes 0.95, the quietest voice is choked. It recovers by 8 partials a block when load is under 0.6.
  - **Offline:** renders never adapt, so exports are repeatable.
- **No allocation while rendering.** A test with a counting allocator fails if eight busy layers allocate during `process`.
- **No speaker-bleed check.** The engine has no bleed detector or bleed meter, in line with its removal from M0.

### CPU load in the worklet

Chrome 154 has no `performance.now()` in the AudioWorklet scope (`typeof performance` is `"undefined"`). The worklet therefore times windows of 16 blocks with `Date.now()` and reports the window's average load once per window. Its 1 ms resolution makes the figure noisy and on the high side: 9 to 42% live, against about 10% measured offline. Because overload starts at 0.8, the noise has not triggered it, but on a slower laptop it could cut the budget early. On blocks between windows the host reports 0, which the engine treats as "no new reading".

## Not in M1, on purpose

- **The live tier inside the new engine** (Live follow on `klont`): M2. The input buffer is in the ABI but unused.
- **Grain cloud** ("use the sound itself", texture sources): M4, with Influence, its only source. The `grain.*` parameters exist and are ignored.
- **Morph lane and states:** M4. **Smear:** v1.
- **The project document, commands, undo, and the compiler from document to tables:** M3. M1 builds tables directly from the demo's data.
- **Storage, the LLM service, Svelte interface:** later milestones.

## Known limits

- **Release and decay are time constants, not fade times.** Both are exponential segments with the TDD's `env.decay` meaning. A sound takes about 7 times its release value to fall 60 dB, and a voice stays busy that long. Long releases on many overlapping notes run a layer out of its 8 voices (the first demo did). Worth deciding before the interface shows these values in seconds.
- **Export tail.** Export stops when the track has ended and output has stayed under -80 dB for 1 s, or 10 s after the end. The demo song always hits the 10 s limit: some tail (reverb, tape or texture noise) stays above -80 dB. Not yet traced.
- **Fixed cost per layer.** At budget 512 the worst case still costs 8.7% of a core in Chrome, so the per-layer work matters as much as the partials: reverb and delay on every layer, 16 noise band-passes per active kit slot, and a sequencer loop that runs per sample over 8 layers. These are the first places to look if the laptop comes in under 4x.
- **The delay's pitch shifter** cancels some tones whose period does not divide half its 50 ms window.
- **Partial jitter** is a fixed random detune drawn at each note start, not a slow drift.

## Open question this milestone answers

The TDD asks: "What partial budget does the reference laptop sustain with 8 layers?" On the build machine, all 4096 partials at 7.9x real time in Chrome. The reference laptop's answer is the "Recommended partial budget" line of `bench.html`, still to be run.
