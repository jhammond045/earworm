# M0: the two prototypes

M0 is throwaway code. It exists to answer two questions from the [TDD](TDD.md) build order, and a person answers them by listening:

1. **Live follow.** Does singing into the page feel good?
2. **Influence match.** Does a matched sound resemble its source?

Nothing past M0 starts until both pass. This page says how to run each prototype, what to listen for, how to settle the two open technical questions M0 owns, and what was measured on the build machine.

## Run it

```sh
pnpm install
pnpm dev
```

Open the URL Vite prints (normally http://localhost:5173). The index page links every prototype and test page and shows whether the page is cross-origin isolated.

- `pnpm dev` serves with `Cross-Origin-Opener-Policy: same-origin` and `Cross-Origin-Embedder-Policy: require-corp`, so the engine uses SharedArrayBuffer rings.
- Add `?fallback=1` to any page URL to force the MessagePort fallback, or run `pnpm dev:nocoi` to serve without the headers at all. The pages show which transport is in use. In the fallback, meters update 30 times a second and capture audio arrives in 100 ms chunks.
- Use Chrome. Wired headphones for Live follow. The browser asks for the microphone on Start, not on load.

The built `engine.wasm` and `analysis.wasm` are committed under `web/public/wasm`, so no Rust toolchain is needed to run the prototypes. If `cargo` is on the PATH, `pnpm dev` rebuilds them first. To rebuild by hand: install Rust from rustup.rs, run `rustup target add wasm32-unknown-unknown`, then `pnpm build:wasm`.

Tests: `pnpm test` runs the TypeScript tests (Vitest) and then `cargo test --workspace`.

## What is in M0

As the TDD asks: the full live tier, a one-layer engine with the partial bank, shaped noise and the vowel-shape path, the tuning function, and the loopback delay measurement. Plus the Influence instant match, so the second question can be asked.

| Piece | Where |
| --- | --- |
| DSP primitives: filters, band bank, YIN, FFT, decimator, noise | `crates/dsp/src` |
| Feature frames (24 floats per 10 ms at 16 bands) | `crates/dsp/src/frame.rs` |
| Live tier (all 14 Live follow requirements, simplified where noted below) | `crates/dsp/src/capture.rs` |
| Tuning: snap, speed, glide/gliss/jump, vibrato, gaps | `crates/dsp/src/tune.rs` |
| One-layer synth: 64-partial bank, shaped noise, vowel path, envelopes, gesture mapping | `crates/engine/src/synth.rs` |
| Engine ABI (`ew_init`, `ew_buffers`, `ew_process`, `ew_render`) | `crates/engine/src/lib.rs` |
| Influence instant match, pYIN second pass, `pitch_eval` tool | `crates/analysis/src` |
| Worklet host, rings, fallback, offline engine | `web/src/host`, `web/src/worklet` |
| Pages | `web/*.html`, `web/src/{live,influence,delay}` |

Not in M0, on purpose: the sequencer and looping, beats and kits, the grain cloud ("use the sound itself"), morphing, macros, the incremental "match while it listens" updates (the match runs once over the whole sound, which takes 10 to 20 ms), Refine, storage, and the LLM service. Influence instant match is pure measurement, so M0 has no server function and no secrets.

## Prototype 1: Live follow

Page: `live.html`. Checklist: `live-test.html`.

Press Start, put on wired headphones and sing. The synth plays as you sing: pitch, loudness and vowel shape drive it. The ribbon shows raw pitch as dots and tuned pitch as a line that thickens with loudness and brightens with openness.

Work through `live-test.html` in a second tab. It rates each item 1 to 5, keeps answers in the browser and downloads them as JSON. What to listen for:

- **Vowels and words.** At Mouth 100%, do "aaa-eee-ooo" and a spoken phrase come through the synth? This is the vocoder test.
- **Swell.** Does "mmmwaaa" get louder and brighter?
- **Delay.** Does the synth feel attached to your voice, or does it trail? Pay attention to note starts: level follows within a block, pitch takes about 25 to 30 ms inside the engine (see measurements).
- **Tuning.** Snap 100% with speed 0 should give hard robotic steps; Snap 50% with 120 ms should sound natural. Try Glide, Gliss and Jump on a slide.
- **Onsets.** Does "ta ta ta" start immediately?
- **Silence.** Is silence silent, with no chatter or breath noise leaking through?
- **Overall.** Does it feel like playing an instrument?

The six presets (Choir pad, Reed, Glass, Buzz, Breath, Bell) give contrasting carriers. "Save last 30 s" downloads the mic audio as WAV, the frames as `.f32` and a JSON of settings. Keep these: they start the hum corpus the TDD wants recorded in M0.

**Pass:** the person singing says it feels like playing an instrument, words come through at Mouth 100%, and the felt delay is "none" or "slight" on wired headphones.

## Prototype 2: Influence match

Page: `influence.html`. Blind test: `influence-test.html`.

Add sounds by file, by drag and drop, or by recording 3 s from the mic. Each sound is matched to a synth parameter set and rendered with the same engine at the source's pitch. Use Play source, Play match, and Play A then B to compare. Audition pitch plays the matched instrument on another note. Sources are saved in the browser (IndexedDB) for the blind test.

What to listen for: does the match keep the source's brightness, its harmonic versus noisy character, its odd/even colour (hollow versus full), and its envelope (plucked, bowed, struck, sustained)? The M0 engine has only sources and envelopes, so motion, grit and space are not matched. The PRD's honest limit applies: 100% is the engine's best match, not a copy.

Blind test: save at least 4 sources (the PRD gate wants 20 varied ones, for example voice, whistle, flute-like, plucked string, bell, drum, clap, hiss, synth pad, bowed sound). Each trial plays one match and four candidate sources; the listener picks the source it was made from. The page scores against the 70% target, shows per-source results, and downloads JSON. The shuffle seed is shown so a run can be repeated.

**Pass:** listeners pick the right source at least 70% of the time across 20 varied sounds (PRD gate).

## Open questions M0 should settle

### 16 or 24 bands?

Both the Live and Influence pages have a 16 / 24 switch. The engine and the frames support either: 16 bands gives the TDD's 24-float frame, 24 bands a 32-float frame.

How to test:

1. In `live.html`, set Mouth 100% and speak or sing the same phrase at 16 and then 24 bands (step 2 of `live-test.html`). The switch restarts the engine and keeps every other setting, so A/B is quick.
2. Try plosives and sibilants ("she sells", "pop tart") and closed vowels ("ee", "oo"), where extra resolution should matter most.
3. In `influence.html`, switch bands and replay the matches of voiced sources; run the blind test once at each setting with the same seed.

Decide 24 only if words are clearly more intelligible or blind-test scores rise. Otherwise keep 16, which is cheaper and matches the TDD frame format.

### Second-pass pitch tracker: pYIN-style or a small neural model?

M0 contains the pYIN-style tracker (`crates/analysis/src/pyin.rs`) and the repair rule from the TDD: replace live pitch where the two differ by more than 80 cents for 30 ms or longer. It does not contain a neural tracker.

How to test:

1. Record the hum corpus with "Save last 30 s": at least 10 untrained voices, varied range, some scoops, vibrato and breathy notes, per the TDD testing plan.
2. Hand-label pitch for each WAV as `<name>.f0.csv` next to it: lines of `time_s,hz`, with 0 Hz for unvoiced. Any frame rate works; the tool interpolates to 10 ms.
3. Run `cargo run -p analysis --release --bin pitch_eval -- <dir>`. It prints, per file and in total: frames voiced by live YIN and by pYIN, their agreement, octave-like disagreements, frames repaired, and, where labels exist, raw pitch accuracy (within 50 cents) and voicing accuracy for live, pYIN and the repaired curve.
4. For the neural alternative, run a small pretrained tracker offline on the same WAVs and score its curve against the same labels. Adding it as a fourth column to `pitch_eval` is a small change.

Choose pYIN unless the neural tracker is clearly more accurate on the corpus, since pYIN needs no model download (the TDD keeps models off the main load path).

## What was measured

Build machine: Apple M4 MacBook Air, Chrome, 48 kHz, 128-frame render quantum.

| Measurement | Result | How |
| --- | --- | --- |
| Engine, voice to output, level | 0 to 1.3 ms (output starts in the same render quantum as the input) | `cargo test -p engine --test live_follow -- --nocapture`, and the same in the browser worklet |
| Engine, voice to output, pitch lock (within 50 cents) | 24 to 28 ms native; 24 to 32 ms in the Chrome worklet, shared and fallback alike | Same tests, synthetic hum at 220 Hz; lock is the start of the first of three 20 ms windows in tune |
| Live tier nominal analysis delay | level 5 ms, pitch 23.5 ms | Engine meters `M_DELAY_LEVEL`, `M_DELAY_PITCH` |
| Live tier measured in isolation | pitch 21 ms, level 2.7 ms | `cargo test -p dsp capture -- --nocapture` |
| Chrome-reported output | `baseLatency` 5.3 ms, `outputLatency` 40 ms (built-in speakers) | `AudioContext` on this machine |
| Influence instant match time | 10 to 20 ms per 1.2 s source in the browser (budget 1 s) | `influence.html` |
| Partial bank cost | about 50 ns per sample at 64 partials plus noise, native | `cargo test --release -p engine synth::tests::bench -- --ignored --nocapture` |
| Device round trip (input plus output) | **not measured** | See below |

**The device round trip still needs a person.** Automated Chrome on the build machine could not open any microphone, real or fake (getUserMedia never resolved, most likely waiting on the macOS microphone permission for the automation-launched browser). So the input-device part of the delay is unmeasured. To finish the number:

1. Open `delay.html` in your normal Chrome.
2. Either connect a loopback cable from output to input, or turn the speakers up near the built-in mic (not headphones; the test needs the mic to hear the output).
3. Press "Run all". The page measures the round trip from five chirps (median and spread), then the engine's internal level and pitch delay from a played test hum, and sums them into a voice-to-ear total against the TDD budget and the PRD's 50 ms target. "Download JSON" keeps the result.

Rough estimate until then, from the TDD's 5 to 15 ms input figure and Chrome's reported output latency: level about 5 + 2.7 + 1 + 40, so 49 to 59 ms; pitch about 5 + 2.7 + 28 + 40, so 76 to 86 ms. Chrome's 40 ms output figure for built-in speakers is an estimate and may be pessimistic; wired headphones on an interface usually report less. If the measured total is over 50 ms, the first place to look is the output device, then the YIN window (32 ms at about 16 kHz), which dominates the engine's share.

## Known simplifications in the live tier

- Requirement 3 (bands between harmonics at high pitch) only handles bands below the fundamental; bands that fall between upper harmonics are not filled.
- The bleed detector is simple and untuned on real speakers: it needs the engine louder than -45 dB, a 200 ms envelope correlation above 0.85, and the mic at least 3 dB below the engine for 100 ms. On bleed the synth mutes and the page asks for headphones.
- Slide detection uses the slow-pitch rate, so a wide (about ±50 cent) 5 Hz vibrato counts as a slide; in Glide that suspends snapping during the vibrato.
- Tune speed lags only the snap correction, not the sung pitch, so at Snap 0 the voice's own pitch passes straight through.
- The analysis code paths for live and stored frames are the same (`frames_from_signal` runs the live tier over a file), but there is no automated live-versus-stored parity test across the worklet yet.
